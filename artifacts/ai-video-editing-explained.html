Part 1 How Claude edits a video today

The whole thing in one picture

In one sentence: A program on your computer turns the video into text, a language model reads that text and writes a list of cuts, and a video tool (ffmpeg) builds the new video from that list.

Keep this picture in mind. Everything below zooms into one of these five boxes. The names change from tool to tool, but the boxes are always there.

How people edit videos with Claude right now

In one sentence: Most people run Claude Code on their own computer, point it at a folder, and let it drive free video tools; a few connect it to a real editing app.

Apps with their own built-in AI (CapCut’s agent, Descript Underlord, OpusClip) are a fifth option, but there Claude is either hidden inside the product or not involved at all. The rest of this part walks through option 1, because the other options are variations of it.

Step by step: what happens after you drop in a video

In one sentence: Claude Code is a loop: the model picks one step, your computer runs it, the result is shown to the model, and it picks the next step until it thinks it is done.

First, two different things called “Claude”

When people say “Claude edited my video”, two separate pieces are involved. Mixing them up is the source of most confusion.

  • The model is the brain. It runs in Anthropic’s data center. It receives text (and sometimes pictures) and writes text back. It cannot run anything, open files, or hear audio. Claude models don’t accept video or audio files at all.
  • The harness is Claude Code itself: an ordinary program on your laptop. It has “hands”: it can run terminal commands, read and write files. It does what the model asks, one step at a time. The harness knows nothing about video. It is the same program people use to write software.

Does it “open the harness”? Yes, the harness is the thing you open

You start Claude Code in a folder (in the terminal or the desktop app). From then on, the harness runs a loop:

How does it know which steps to take? Is that built into the model?

Only general knowledge is built in. The model learned during training what ffmpeg is, how Whisper transcription works, and what a jump cut is. It was also trained to work in this loop, using tools step by step. But nobody built a video-editing program into it. The actual workflow comes from one of two places:

  • A recipe (“skill”) file that you installed: a long text document like video-use’s 340-line SKILL.md, with rules such as “pad every cut by 30–200 ms” and “show me the plan before rendering”. The harness pastes it into the conversation, and the model follows it like a checklist.
  • Improvisation when there is no recipe. The model invents a plan from general knowledge, which is why results vary so much between people and between runs.

The steps it actually takes (a typical talking-head edit)

The time estimates are illustrative, for a 14-minute 4K talking-head recording on a laptop.

  1. 1
    You

    You ask

    “Here’s raw.mp4. Cut mistakes and long pauses, keep it under 8 minutes, add captions.”

  2. 2
    ModelHarness

    Look at the file

    The model asks the harness to inspect the file. It learns the length, resolution, frame rate, codec and audio format: facts it needs before touching anything.

    ffprobe raw.mp4
  3. 3
    ModelHarness

    Pull out the audio

    Transcription only needs sound, so it copies the audio track into its own file. This takes seconds.

    ffmpeg -i raw.mp4 -vn -ac 1 -ar 16000 audio.wav
  4. 4
    HarnessSpeech model

    Transcribe, with a time for every word

    A speech-to-text model (Whisper on your laptop, or a paid service like ElevenLabs Scribe) writes down every word with its start and end time. This is the single most important file in the whole process. Takes about 1–3 minutes.

    {"word": "today", "start": 2.95, "end": 3.28}
  5. 5
    Model

    Read the transcript and decide (the “planning”)

    The model reads the transcript, often compressed into short phrases with times, and spots retakes (the same sentence said twice), rambling, long pauses and filler words. This is the only part that really needs a smart model.

  6. 6
    ModelHarness

    Optionally, look at a few pictures

    Because it can’t watch, it may ask for a “contact sheet”: one image with a grid of frames, or a filmstrip around a cut point. That is how it checks framing or spots someone walking into shot.

    ffmpeg -i raw.mp4 -vf fps=1/10,scale=320:-1,tile=6x4 sheet.png
  7. 7
    Model

    Write the cut list

    It writes down which time ranges to keep. That small text file is the whole edit.

    keep 0.00–0.45
keep 2.95–41.20
keep 44.80–97.35 ...
  8. 8
    HarnessYour computer

    Render

    ffmpeg cuts each kept range, adds tiny audio fades so cuts don’t click, joins the pieces, and burns in captions. Every frame is re-encoded, so a long 4K video can take many minutes. This is where your laptop fans spin.

  9. 9
    ModelHarness

    Check its own work (if the recipe says so)

    Good recipes re-transcribe the finished video or look at frames around each cut to catch clipped words or black frames, then fix and re-render. Without a recipe this step is often skipped.

  10. 10
    ModelYou

    Report back

    It writes something like “Done: final.mp4, 7:48. Removed 41 pauses and 3 retakes.” The result is just a new file in your folder. Nothing is sent to you; you open it in your video player.

  11. 11
    You

    Give feedback, and the loop starts again

    “The cut at 2:13 is too abrupt.” The model edits the cut list and usually re-renders the whole video. Most of the real time goes into these rounds.

What is “the planning call”?

In one sentence: It’s one request to the model that says “here is everything we know about the footage, give me back the edit as structured data”. Claude Code doesn’t have one; a product would.

In Claude Code there is no separate planning call. Planning is smeared across dozens of loop steps: look, think, try, fix. That is flexible, but slow, expensive, and different every time.

In a product pipeline, the boring steps (transcribe, find pauses, find shots) run as normal code with no AI decision-making. Then you make one call to the model with everything packed in, and you demand the answer in a strict format your code can check:

What you send (simplified)

Instructions: tighten this talking-head video to
under 8 minutes. Remove retakes, fillers, pauses
over 0.6 s. Never cut mid-sentence.
Return JSON only, in the format below.

Footage summary:
[000.00-006.20] A: So, um, today we're going to—
[007.80-014.50] A: sorry. Today we're editing...
pauses: 6.2–7.8, 14.5–16.9
shots: 0–12 (face centre), 12–21 (B-roll)...

What comes back

{
  "keep": [
    {"from": 0.00, "to": 0.45},
    {"from": 7.95, "to": 14.50,
     "reason": "second take is cleaner"}
  ],
  "zooms": [{"at": 42.1, "scale": 1.15}],
  "estimated_length": 467
}

Then plain code checks the answer: are all cuts in silence, is the length under 8 minutes, are no words clipped. Only after that does it render. One smart call plus a lot of plain code is faster, cheaper and more predictable than letting the model wander through a loop. That is the “better way” the previous report described. If you go the MCP route (Part 4), you can skip building this yourself: the user’s Claude Code becomes the planner, and your app supplies the summary and the checks.

What goes wrong today

In one sentence: The model is blind and deaf, cuts are imprecise, every change means re-rendering, and there is no timeline for a human to nudge.

  1. It’s blind and deaf. It knows only what the transcript and a few still pictures tell it, so it misses a bad facial expression, a dog barking or someone walking into frame.
  2. Timestamps are slightly wrong. Word times can be 50–500 ms off, so cuts clip the start or end of words (picture below).
  3. It cuts in odd places and miscounts. Cuts land mid-sentence, and its arithmetic on durations is unreliable: in one vendor test it said 299 s when its cuts added up to 578 s.
  4. Every fix re-renders everything. Small feedback can cost minutes of waiting on long or 4K videos.
  5. There’s no timeline. You give feedback by typing “at 2:13…” instead of dragging a cut by hand.
  6. It says “done” too early. In one 2026 benchmark, agents claimed success in 93% of runs, but even the best finished only about 1 in 4 real editing tasks.
  7. Taste. Pacing, emotion, choosing B-roll by how it looks, and music timing are the weakest areas.
  8. Big files. 4K footage is gigabytes: slow to upload to cloud sessions and slow to render on a laptop.
  9. Setup. You need a terminal, ffmpeg, a transcription tool and sometimes API keys, which is a wall for normal creators.
  10. Cost and limits. Long loops with screenshots eat through subscription limits quickly.
Part 2 Video technology, simply

What a video file actually is

In one sentence: A video file is a box holding separately compressed picture and sound tracks; the compression stores one full picture now and then, and only the changes in between.

Why codecs exist

How the compression works (and what “only writing down the difference” means)

Most frames in a video look almost exactly like the frame before. Your face moved a few pixels, the background didn’t move at all. So the codec stores:

  • Keyframes (also called I-frames): a complete picture, like a JPEG photo. Usually one every 1–10 seconds.
  • Difference frames (P- and B-frames): instructions like “take this block from the previous picture, shift it 3 pixels left, brighten it slightly”. They are tiny. B-frames can even borrow from the frame after them.

The group from one keyframe to the next is called a GOP (group of pictures).

Encoding is packing: deciding what changed and writing the notes. It’s slow and is where you trade quality against file size. Decoding is unpacking. It’s fast, and most computers have a dedicated chip for it. Your Mac or an NVIDIA graphics card also have hardware encoders: chips that pack video very fast at slightly lower efficiency.

What this means for editing

  • Cutting exactly where you want usually means re-encoding at least the frames around the cut, because the cut point may sit on a “notes” frame.
  • Professional editing codecs (ProRes, DNxHR) make every frame a keyframe. The files are huge, but cutting and scrubbing are instant. That is why editors convert footage to these.
  • Every re-encode loses a little quality (“generation loss”), so good pipelines encode the final output once, from the originals.

What ffmpeg does

Codec normalisation: cleaning up phone footage first

Phones and cameras produce messy files. Normalising means converting them once, on import, into one predictable format so every later tool agrees on timing.

Problem in the raw fileWhat goes wrongNormalise to

Low-res proxies, explained

In one sentence: A proxy is a small, light copy of your video, used for everything except the final render.

Think of it like a photo thumbnail. You browse and choose using the thumbnails, then print the full-resolution photo. Professional editors have worked this way for decades: Premiere and DaVinci Resolve both have a “proxy” button.

What a good editing proxy looks like: 540p or 720p, H.264, a low bitrate, and keyframes close together (every frame, or every half second) so jumping around is instant. It’s made once on import, using the computer’s hardware encoder.

Why proxies matter even more for AI:

  • Transcription only needs the audio. Face, shot and caption models work on small pictures anyway.
  • Uploading 300 MB instead of 10 GB is the difference between seconds and many minutes.
  • Gemini shrinks each frame to a fixed small size anyway, so sending 4K mostly wastes upload time (see below).
  • Live preview in your app plays the proxy, so it stays smooth even on a laptop.
Part 3 How a model perceives video

Helping the model “see”: the senses

In one sentence: A set of small, specialised tools each measure one thing about the footage, and their results are lined up on one timeline and handed to the model as text.

You’re right that transcription is the obvious first sense, but it is only one of several. Here is the same clip seen through all of them:

Transcription (ASR) + word timing

What it is: Speech-to-text. ASR stands for automatic speech recognition.

How it works: A speech model listens to the audio and writes the words. A second step (“forced alignment”) pins each word to its exact start and end time.

It produces: {"word":"today","start":2.95,"end":3.28}

Why an editor needs it: It is the spine of a talking-head edit. Every cut, caption and retake decision starts here.

VAD: voice activity detection

What it is: A detector for “someone is speaking” versus “silence or background noise”.

How it works: A tiny neural network (Silero VAD) looks at 30-millisecond slices of audio and says speech or no speech. It runs faster than a millisecond per slice on an ordinary CPU.

It produces: speech 0.5–6.2, 7.8–14.5 … pause 6.2–7.8

Why an editor needs it: It finds dead air to remove, and it finds safe places to cut: in the silence between words, not inside them.

Fillers

What it is: Detecting “um”, “uh”, stutters and false starts.

How it works: Many transcription models quietly delete fillers to make a clean transcript, which is bad for editing. You need a “verbatim” model (for example CrisperWhisper) that keeps them with timestamps. Removing them is then a simple list filter.

It produces: {"word":"um","start":0.45,"end":0.80,"filler":true}

Why an editor needs it: Tightening speech is the most common edit request. Miss the fillers and the edit sounds sloppy.

Diarisation (who spoke when)

What it is: Labelling each stretch of speech with a speaker: A, B, C…

How it works: A model (pyannote) turns short audio slices into “voice fingerprints” and groups similar ones together. It doesn’t know names, only that A is the same voice as earlier A.

It produces: A 0.5–14.5 · B 16.9–23.0 · A 23.6–29.5

Why an editor needs it: Podcasts and interviews: cutting to whoever is talking, removing the interviewer’s questions, giving each speaker their own caption colour.

Shots (scene detection)

What it is: Finding where the picture suddenly changes: a camera switch, a new clip, a jump to B-roll.

How it works: Compare each frame with the previous one. A big jump in colours or content means a new shot. Simple tools (PySceneDetect) compare colour histograms; neural ones (TransNetV2) also catch fades and dissolves.

It produces: shot 1: 0–12.0 · shot 2: 12.0–21.0 · shot 3: 21.0–30

Why an editor needs it: Shows the structure of the footage, avoids cutting a shot one frame before it ends, and splits B-roll into usable pieces.

Faces

What it is: Where each face is in the frame, for every frame (or a few per second).

How it works: A face detector (Apple Vision, MediaPipe) draws a box around faces. Tracking links boxes across frames into “the same person”.

It produces: t=4.0 face box x 0.42 y 0.20 w 0.17 h 0.36

Why an editor needs it: Reframing to vertical, centring punch-in zooms, noticing when you look away or leave the frame.

Visual captions

What it is: A short written description of what’s on screen in each shot.

How it works: A vision-language model (Gemini Flash, Qwen-VL) looks at a few frames per shot and writes a sentence. This is how a text-only model “sees”.

It produces: 12.0–21.0: hands typing on a laptop, close-up, warm light

Why an editor needs it: Lets the brain choose B-roll (“find the shot of typing”), notice visual mistakes, and match visuals to what’s being said.

Embeddings

What it is: A list of numbers (a “meaning fingerprint”) for each shot, frame or sentence.

How it works: A model like CLIP turns images and text into numbers in the same space, so similar meanings get similar numbers. Search becomes “find the nearest numbers”.

It produces: shot 2 → [0.12, -0.43, 0.88, … 512 numbers]

Why an editor needs it: Searching footage by meaning, finding B-roll, and spotting two takes of the same sentence (their text embeddings are almost identical).

Putting it together: the dossier

All of these outputs are merged into one compact text summary of the footage. That “dossier” is what the model actually reads. Designing it well is a real skill and a real source of advantage. Too little detail and the model guesses; too much and it drowns (and costs more).

[02.95–14.50] A (you), face centre, shot 1 "man at desk":
   "Today we're editing with Claude. [pause 0.4] The trick is…"
   fillers: um@9.4
[14.50–16.90] SILENCE 2.4s  ← safe cut
[16.90–23.00] B (guest), no face on screen, shot 2 "hands typing, laptop":
   "Wait, so it never actually watches it?"

Sending the video to Gemini instead

In one sentence: Gemini can genuinely take video, so for “what is on screen” it’s great; for exact cut points the senses route is better. Either way, send it the low-res proxy.

Send the video to GeminiSenses → text dossier → Claude
What it understandsWhat’s visible and audible; scenes, actions, on-screen textOnly what the sensors measured, plus captions if you add them
Timing precisionAbout ±1 second (it samples 1 frame per second by default)Word-exact (tens of milliseconds)
Cost for 10 minutes~$0.05–0.14 at Flash prices (≈100–300 tokens per second of video)Mostly free (local) plus about 2–15K tokens of text
UploadThe file must be uploaded first, so a small proxy mattersNothing uploaded except text
Best used forShot captions, finding highlights, “is anything weird on screen?”Cut decisions, pauses, retakes, captions

Your instinct about low resolution is right. Gemini scales each sampled frame down to a fixed small size. Its default costs about 258 tokens per frame, or about 66 at its “low” media resolution setting. A 4K upload therefore buys almost nothing over 540p, except when you need to read small on-screen text. It just takes far longer to upload.

Streaming isn’t necessary. A 540p proxy of a 10-minute video is roughly 100–300 MB and uploads quickly. A practical recipe is to make the proxy, send it to Gemini once, and ask for a caption per shot with timestamps. Merge that into the dossier and let the exact timing come from the audio senses.

The timeline data model: JSON and the “source of truth”

In one sentence: Instead of the edit existing only as a rendered video, it lives as a small text recipe (written in JSON) that both you and the AI edit, and the video is cooked from it.

What is JSON?

JSON is just a way of writing structured information as plain text, so both people and programs can read it. It uses { } for a thing with named properties, [ ] for a list, and "name": value pairs. That’s nearly all of it.

A tiny timeline in JSON

{
  "sources": [
    {"id": "A", "file": "raw.mp4",
     "proxy": "raw_540p.mp4"}
  ],
  "video": [
    {"source": "A", "in": 0.00, "out": 0.45},
    {"source": "A", "in": 7.95, "out": 312.4,
     "zoom": {"scale": 1.15, "follow": "face"}}
  ],
  "captions": {"style": "bold-yellow"},
  "music": {"file": "lofi.mp3", "volume_db": -18,
            "duck_under_voice": true}
}

The same thing in plain words

  • There is one source file, raw.mp4, with a small copy for previews.
  • Clip 1: play raw.mp4 from second 0.00 to 0.45.
  • Clip 2: then play it from 7.95 to 312.4, zoomed in 15% and following the face.
  • Add captions in the “bold yellow” style.
  • Play lofi.mp3 quietly underneath, and lower it automatically whenever someone speaks.

Notice what’s not in there: no pixels. The recipe is a few kilobytes even for an hour of video. Rendering means “cook this recipe into an mp4”. Premiere and Resolve store projects the same way, and there are standard formats for it (OpenTimelineIO, FCPXML) so you can hand a recipe to another editor.

“Source of truth”

The phrase just means “the one copy everybody trusts”. If the mp4 were the truth, every change would mean re-rendering and you couldn’t undo the AI’s fourth change while keeping its fifth. With the recipe as the truth, you get undo history, instant previews, side-by-side versions, re-rendering only what changed, and export to Premiere. You can also see exactly what the AI did.

Why the audio is the “spine”

For talking-head videos, most editing decisions are about what is said. That is why the transcript (from the audio) is the best way to steer the edit. The recipe stays the truth; the transcript is the friendliest window onto it, for you and for Claude alike.

Seeing the edit before it’s rendered (your streaming idea)

In one sentence: Yes: you don’t have to wait for a render at all. Play the recipe live from the proxies, and let the user watch the timeline change as Claude works.

  • Stream chunks while rendering. Render the video in short pieces in order, and start playing piece 1 while piece 2 is still being made, the way YouTube streams. This is a real improvement over waiting.
  • Even better: don’t render to preview. A player can follow the recipe directly: “play raw.mp4 0.00–0.45, then jump to 7.95…”, drawing captions and zooms on top in real time. Every professional editor works like this. You only render once, when exporting. On a Mac, Apple’s own video framework (AVFoundation) can play a list of time ranges from source files as if it were one video, without rendering.
  • “Watching the work” is a great product idea. Every time Claude calls a tool (“remove pause at 2:10”), the timeline in your app visibly changes, the playhead jumps there, and a side panel says what happened and why. The user can stop it, undo one change, or grab a cut and drag it. This fixes several problems from the list above at once: no blind waiting, no re-render per fix, and feedback by dragging instead of typing timecodes.
Part 4 Building it

Your idea: a beautiful native app plus local MCP

In one sentence: Your app is the eyes, hands and screen; the user’s own Claude Code or Codex is the brain, plugged in through a local MCP server.

I agree with skipping the planner and router for a first version. Going MCP-first means you don’t pay for the thinking (the user’s subscription does, which Anthropic’s rules allow because the user runs their own Claude Code). You also don’t compete with Claude Code; you make it good at video.

What MCP is, in one paragraph

MCP (Model Context Protocol) is a standard plug-in system for AI tools. Your app ships a small MCP server that runs locally on the same Mac. The user adds it to Claude Code or Codex once, with a single setup command. From then on Claude sees your tools in its tool list, exactly like it sees “run a terminal command”. When Claude calls cut, your app does the work and replies with a short text result. No video ever goes to the model, only your compact text. Optionally a small image goes too, such as a filmstrip around a cut.

The tools you would expose

ToolWhat Claude asksWhat your app returns
get_overview“What is this project?”Length, speakers, shots, a short dossier summary
get_transcript(range)“Show me 2:00–4:00”Phrases with times, fillers and pauses marked
look(times)“Let me see around 2:13”One small filmstrip image
keep_only / remove(ranges)“Remove these pauses and that retake”“Done, new length 7:48”; the timeline animates
zoom / caption_style / add_music“Punch in 15% on the joke”Confirmation; the change is visible live
find_broll(query)“Find a shot of typing”Top matches from the embeddings search
check()“Any problems?”Clipped words, cuts inside speech, jumps in loudness
export(preset)“Render for YouTube and Shorts”File paths when done

Why this is better than a recipe file: the rules that recipes ask the model to remember (pad every cut, add fades, never cut inside a word, check loudness) become code in your app. The model literally can’t clip a word, because your remove tool snaps every cut to the nearest silence. Reliability moves from “hope the model follows the instructions” to “guaranteed by the software”, and that is real value Claude Code can’t give you out of the box.

For a pretty, simple, fast creator tool, native Mac first is a reasonable bet. Most of the senses come nearly free and run on-device: Apple’s Vision framework for face detection and image “fingerprints” (embeddings), its Speech framework or open-source WhisperKit for transcription, VideoToolbox for hardware encoding, and AVFoundation for live playback of an edit list. That means no server bill, private footage, and it works offline. Windows can come later.

A day in your app

  1. The creator drags raw.mp4 into the app. It normalises the file and makes a proxy in the background (about a minute).
  2. The senses run on the Mac. A progress bar fills: transcribing, pauses, speakers, shots, faces.
  3. In Claude Code (or a chat panel that talks to it) they type: “tighten to under 8 minutes, keep my jokes, captions in my usual style.”
  4. They watch the timeline shrink as Claude calls remove again and again, each change labelled with a reason.
  5. They drag one cut back by half a second and tell Claude: “you cut the punchline, put it back.”
  6. They press Export. The hardware encoder renders 4K from the originals once.

The genuinely hard parts (where your effort goes)

  • A frame-accurate timeline that both a person and Claude can edit without conflicts, with undo.
  • Preview that matches export exactly (captions, zoom curves, audio fades).
  • Every weird camera file (normalisation is an endless list of edge cases).
  • Tool design, so Claude doesn’t flail: few tools, compact answers, clear errors.
  • Onboarding: your users need Claude Code or Codex installed and connected. Consider a built-in chat panel that uses their Claude Code under the hood, so non-terminal people never see a terminal.
  • Mac only at first, which is a choice of market, not just of technology.

Glossary

Agent loop
The model picks one step, the harness runs it, the result goes back, repeat.
ASR
Automatic speech recognition: speech-to-text.
Codec
The packing method for picture or sound (H.264, HEVC, AV1, ProRes, AAC).
Container
The file “box” holding tracks (.mp4, .mov, .mkv).
Contact sheet / filmstrip
One image made of many small frames, so a model can “see” a stretch of video at once.
Cut list / EDL
The list of time ranges to keep, in order. EDL stands for edit decision list.
Diarisation
Working out who spoke when.
Dossier
The compact text summary of everything the senses found.
Embedding
A list of numbers representing meaning; similar things get similar numbers.
ffmpeg
The free, universal command-line tool that reads, changes and writes almost any video.
GOP
Group of pictures: one keyframe plus the difference frames until the next keyframe.
Harness
The program around the model that runs tools: Claude Code, Codex, or your app.
JSON
A plain-text way to write structured data with { }, [ ] and "name": value.
Keyframe (I-frame)
A frame stored as a complete picture.
MCP
Model Context Protocol: a standard way for apps to offer tools to AI agents.
Normalisation
Converting messy camera files into one predictable format on import.
Proxy
A small, light copy of a video used for analysis and preview.
Render / encode
Cooking the recipe into a finished video file.
Skill / recipe
A text file of instructions (plus small scripts) that teaches an agent a workflow.
Source of truth
The one file everybody trusts; here, the timeline recipe.
Stream copy
Re-boxing video without re-encoding: instant, but cuts only at keyframes.
VAD
Voice activity detection: speech versus silence.
